Front-end

Fluxo de inscrição no navegador

A interface só confirma depois que a API grava; quem decide as regras é o servidor.

  1. Carregar eventos: GET /api/eventos (cache: 'no-store') e montar os cards.
  2. Selecionar: só eventos futuros e com vagas habilitam o envio.
  3. Enviar: POST /api/eventos/{id}/inscricoes; botão vira “Confirmando...” e fica desabilitado (evita clique duplo).
  4. Sucesso (201): grava o resumo no sessionStorage e abre o comprovante.
  5. Erro (400/409/422): exibe a mensagem devolvida pela API, ex.: “Este e-mail já está inscrito no evento.”
const resposta = await fetch(
  `${API_EVENTOS}/${encodeURIComponent(escolhido.id)}/inscricoes`, {
    method: 'POST',
    headers: {'Content-Type': 'application/json'},
    body: JSON.stringify({participante: {nome, email}})
});
const dados = await resposta.json().catch(() => ({}));
if (!resposta.ok) {
  throw new Error(dados.mensagem
    || `Erro ${resposta.status} ao confirmar inscrição.`);
}
// Só exibe o comprovante depois que a API confirmou.
sessionStorage.setItem('semana_academica_inscricao_confirmada_v1',
  JSON.stringify(resumoInscricao));
location.assign('/inscricao-confirmada/');
Front-end

Boas práticas aplicadas na interface

Segurança, acessibilidade e robustez sem dependências externas.

Segurança

  • Conteúdo da API inserido com textContent, sem interpretar HTML (evita XSS)
  • Dados pessoais fora da URL
  • Tabela de inscritos depende da autorização do back-end: o visitante recebe 403 e vê só um aviso

Acessibilidade

  • Campos com <label> associado
  • Mensagens em role="status" e aria-live="polite"
  • aria-busy no formulário durante o envio
  • lang="pt-BR" e datas formatadas em pt-BR

Robustez

  • Estados de carregando, lista vazia e erro de conexão
  • Valida formato da resposta (Array.isArray)
  • Validação nativa do HTML5 (required, type="email")
  • Lista recarregada após inscrever para atualizar as vagas

Regras de negócio e concorrência

Duas pessoas disputando a última vaga: só uma é confirmada, a outra recebe 409.

Ordem de validação da inscrição

  1. JSON válido e objeto → senão 400
  2. Nome e e-mail válidos → senão 400 com campos
  3. Evento existe → senão 404
  4. Evento não começou → senão 422
  5. E-mail inédito no evento → senão 409
  6. Há vaga → senão 409
  7. Cria e devolve 201
Back-end

Segurança e proteção de dados

Nomes e e-mails dos participantes só são expostos a organizadores autenticados.

Autenticação

  • Sessão Django; login pelo formulário do Django Admin
  • Organizador = usuário com is_staff=True
  • /organizacao/ usa @staff_member_required
  • Endpoints restritos respondem 403 ACESSO_NEGADO

CSRF

  • Cadastro de evento e cancelamento exigem token CSRF de sessão válida
  • Inscrição pública usa @csrf_exempt: é anônima, sem sessão a proteger
  • CSRF_TRUSTED_ORIGINS com o domínio da Azure

Validação e configuração

  • Validação no servidor: e-mail, datas com fuso, capacidade inteira ≥ 1
  • Segredos somente em variáveis de ambiente
  • Cabeçalhos: X-Frame-Options: DENY, nosniff, COOP
  • HTTPS reconhecido atrás do proxy (SECURE_PROXY_SSL_HEADER)

Arquitetura da automação Playwright

Integrada ao repositório, com projetos separados para API e interface.

Como uma execução funciona

  1. O Playwright sobe o Django numa porta dedicada com banco SQLite descartável, nunca o PostgreSQL
  2. Aplica as migrações e cria um organizador temporário com senha aleatória
  3. Faz login uma vez por worker (sessão + CSRF) e reaproveita os cookies
  4. Roda api e interface em paralelo, com 7 workers
  5. Gera relatórios HTML e JUnit, além de screenshot, vídeo e trace das falhas

QA

Desafios técnicos resolvidos

Problemas de ambiente investigados por medição, sem aumentar tempos limite às cegas.

Páginas levando 3 s

Pelo curl o servidor respondia em milissegundos, mas no navegador cada página demorava ~3 s.

Causa: o cabeçalho Cross-Origin-Opener-Policy força um processo novo no Chromium, e o antivírus da máquina deixa isso lento.

Solução: flag no navegador de teste, de 3.000 ms para 27 ms; a presença do cabeçalho segue validada nos testes de API.

Concorrência no SQLite

O SQLite ignora o select_for_update do PostgreSQL e gerava “database is locked” com testes paralelos.

Solução: transaction_mode=IMMEDIATE na DATABASE_URL de teste, sem mudar a aplicação.

Testes interferindo entre si

A limpeza de um teste apagava eventos que outro teste ainda estava carregando.

Solução: dados únicos por teste e, nas tabelas de inscritos, a página só enxerga os eventos do próprio teste (resposta real da API, filtrada).
